### FINDING [low] The new urlparse() call in end_headers crashes error responses for request targets it cannot parse
- file: /home/akaihola/prg/drum-transcribe/src/drum_transcribe/serve.py:1621
- scenario: A LAN client (or scanner) sends `OPTIONS http://[x/ HTTP/1.1`, or `GET http://[x/ HTTP/1.1` with more than 100 headers. parse_request has already set self.path. send_error(501/431) then calls end_headers, where `urlparse(getattr(self, "path", ""))` raises `ValueError: Invalid IPv6 URL`. The client gets no response at all, and a traceback goes to the service log. Before the change the old end_headers never parsed the path, so these requests got proper 501/431 replies. The getattr guard only covers a missing path, not one that urlparse rejects. Impact is limited to dropped error replies and log noise. Browsers and Cloudflare always send origin-form paths, so this can't be used to get around the sandbox headers.
- evidence: Ran $TMPDIR/probe/garble.py with raw sockets against the real AppHandler, once with the working tree and once with a HEAD copy of the package (PYTHONPATH=$TMPDIR/oldpkg). NEW: `OPTIONS absolute-form bad IPv6 -> b''` and `GET bad IPv6 + 120 headers (431) -> b''`, each with `ValueError: Invalid IPv6 URL` raised from end_headers. OLD: `HTTP/1.0 501 Unsupported method ('OPTIONS')` and `HTTP/1.0 431 Too many headers`. A POST with the same target crashes in do_POST in both versions, so that case is not new.
- suggested fix: Make the /files/ test unable to raise. Either wrap it in `try: ... except ValueError:` and treat an unparsable target as /files/ (fail closed), or set a flag (e.g. `self._sandbox = True`) in the `elif path.startswith("/files/")` branch of do_GET and check that flag in end_headers. A flag set at routing time also makes the header exactly match the requests that _send_file serves.

### VERDICT real=True in_scope=True: Every link download, lossy ones included, is now re-encoded to 24-bit FLAC: 5-10x larger, and the page must download all of it before the first play
I reproduced it. I ran the new ffmpeg arguments on output/dancing-through-life/taustanauha/source.mp3 (320k, 48 kHz, 7.3 MB) saved as fetched.bin. The result is source.flac at 36.5 MB, and ffprobe reports flac s32 with bits_per_raw_sample=24. Before the change (34d262f), _download named a direct .mp3 link fetched.mp3 and _as_source just renamed it to source.mp3, byte for byte. Now every urllib download is fetched.bin, so it always goes through FLAC conversion. The cost reaches users: LocalRecording.initialize() (static/local-recording.js:617-626) fetches the whole version.source and runs decodeAudioData before play, seek or backing selection can proceed, and the README says the original uses the downloaded audio. On the cloud site, _send_file 302-redirects audio stand-ins to gate.presigned(), which signs a fresh URL on every request, so the 5x larger file is downloaded again on each visit. The rented GPU host also pulls the 5x larger file from the bucket. Nothing in the change accepts this cost. The comment justifies FLAC with 'a link may well be a .wav', and the README shows the project cares about served audio size: drumless moved to Opus, '7x smaller than lossless FLAC'. Two corrections to the scenario. The Drive part is not a regression: the locked gdown 6.4.0 has no 'fuzzy' kwarg, so Drive links raised TypeError before the change, and deploy/Dockerfile doesn't install gdown at all. WAV links actually get smaller. The direct-link MP3/AAC/Ogg case is real and introduced by this change. The impact is size and latency only; nothing breaks.

### VERDICT real=False in_scope=True: In-app help for the original still says the link's audio is kept 'untouched'
The string at serve.py:694 has not changed and is accurate in substance. In context, 'untouched' sets the original against the processed tracks (the Demucs-separated drums, the sonifications). FLAC is lossless, so the stored samples match the decoded link audio. Mono copied to two channels sounds the same. A multichannel downmix is the only audible change, and that is a rare edge case for music links; video inputs were already downmixed with -ac 2 before. 'Untouched' was already loose before the change: YouTube links, the most common link type, are transcoded to MP3 by yt-dlp, and video links became AAC .m4a. The page has no download link for the original (only drumless gets one), so the '36 MB .flac when saving the original' scenario rests on the browser's own audio-control menu. The real issue, a file several times bigger, is covered by the first finding. Fixing that one (keep the lossy stream as it is) also keeps this wording true. On its own this is a wording nit, not a defect. A previous verifier reached the same conclusion on the same finding (docs/files-xss-handoff.md:101-102).
